# Захист секретів у проєкті

**Секрет** — це конфіденційне значення, яке дає доступ до облікового запису або сервісу. До секретів належать Telegram bot token, API-ключі, паролі та `DATABASE_URL` із даними для підключення до бази.

Не записуй секрети безпосередньо в код і не надсилай їх у GitHub. Якщо стороння людина отримає токен, пароль або URL бази з обліковими даними, вона може скористатися відповідним ботом, API чи базою даних.

## Файли конфігурації

- **`.env`** зберігає справжні значення локально на комп’ютері. Не додавай цей файл до Git.
- **`.env.example`** показує, які змінні потрібні проєкту, але містить лише порожні значення або приклади-заповнювачі, наприклад `BOT_TOKEN=встав_токен_сюди`.
- **`.gitignore`** вказує Git, які локальні файли не потрібно додавати до репозиторію. У цьому проєкті в ньому має бути `.env`.

## Якщо секрет потрапив у репозиторій

1. Негайно відклич або заміни секрет: створи новий bot token у BotFather, перевипусти API-ключ, зміни пароль або онови облікові дані бази.
2. Запиши нове значення тільки в локальний `.env` або сховище секретів; переконайся, що `.env` ігнорується Git.
3. Прибери секрет із коду та комітів. Простого видалення файлу в новому коміті недостатньо: секрет може залишатися в історії Git, тому за потреби очисть історію репозиторію та перевір копії й логи.
4. Перевір репозиторій сканером секретів, наприклад `detect-secrets`.

Вважай секрет скомпрометованим навіть після видалення з видимого файлу. Спершу відклич його, а вже потім очищай історію.

## Структура бази даних за діаграмою dbdiagram.io

База даних PostgreSQL у Neon містить таблиці для користувачів, каталогу книг, настроїв і результатів пошуку. Первинний ключ (`PK`) унікально визначає рядок, а зовнішній ключ (`FK`) пов’язує його з рядком в іншій таблиці.

### Таблиці

- **`users`** — користувачі бота. `id` — внутрішній PK; `telegram_id` — унікальний ID користувача Telegram; `username` — ім’я користувача, якщо воно є; `created_at` — час створення запису.
- **`books`** — каталог книг. Містить PK `id`, обов’язкову `title`, а також `author`, `description`, `publication_year` і `cover_url`.
- **`moods`** — довідник настроїв, за якими шукають книги. `id` — PK, `name` — унікальна назва настрою.
- **`genres`** — довідник жанрів. `id` — PK, `name` — унікальна назва жанру.
- **`mood_searches`** — запити користувачів на підбір книги. `user_id` — FK до `users`; `mood_text` зберігає введений користувачем текст; необов’язковий `matched_mood_id` — FK до розпізнаного настрою; `created_at` — час запиту.
- **`book_moods`** — проміжна таблиця для зв’язку книг із настроями. Складений PK утворюють `book_id` (FK до `books`) і `mood_id` (FK до `moods`).
- **`book_genres`** — проміжна таблиця для зв’язку книг із жанрами. Складений PK утворюють `book_id` (FK до `books`) і `genre_id` (FK до `genres`).
- **`recommendations`** — книги, запропоновані у відповідь на запит. `mood_search_id` — FK до `mood_searches`; `book_id` — FK до `books`; `position` визначає порядок книги у списку рекомендацій.

### Зв’язки між таблицями

- Один користувач (`users`) може мати багато запитів (`mood_searches`), а кожен запит належить одному користувачу.
- Один запит може бути зіставлений з одним настроєм (`moods`); один настрій може відповідати багатьом запитам.
- Книга може мати кілька настроїв, а один настрій може підходити багатьом книгам. Цей зв’язок «багато до багатьох» зберігає `book_moods`.
- Книга може належати до кількох жанрів, а один жанр може мати багато книг. Цей зв’язок зберігає `book_genres`.
- Один запит може повернути кілька рекомендацій; кожен рядок `recommendations` пов’язує конкретний запит із конкретною книгою.

Потік підбору: користувач надсилає настрій → бот зберігає його в `mood_searches` → зіставляє з `moods` → знаходить книги через `book_moods` → зберігає порядок результатів у `recommendations`.
